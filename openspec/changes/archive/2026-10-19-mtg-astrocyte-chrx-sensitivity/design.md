# Design

## Context

See `proposal.md` for the motivation. The state that shapes the approach:

- **The export step** (`run_export`, archived change `2026-10-16-mtg-astrocyte-motco-export`) loads the two count matrices, the donor table and the covariates once, then runs the per-cohort body inline: restrict to the cohort, `smallest_cell` → `k`, `preprocess_block` per omic, write the seven files into `<cohort>.tmp/`, rename. `preprocess_block` already takes `excluded_chromosomes` as a keyword (default `EXPORT_EXCLUDED_CHROMOSOMES`), but the per-cohort body passes nothing and the manifest writes `list(EXPORT_EXCLUDED_CHROMOSOMES)` directly. Removed features are labelled `sex_chromosome` in `features_<omic>.csv` whatever the excluded set (chrM included), and the spec's determinism requirement makes the export CSVs byte-identical across reruns.
- **The analysis step** is already a shared helper: `_analyze_cohort(cohort, cohort_dir, loaded, params, *, out_dir, final_name, n_jobs, findings, published_dir, log_prefix)` takes the export directory the inputs were read from (recorded in the manifest and in `cli_equivalent`), and `run_analysis` calls it with `TrajectoryAnalysisParams(permutations=ANALYSIS_PERMUTATIONS, seed=ANALYSIS_SEED, n_jobs=n_jobs)`. Its manifest copies the export manifest's `thresholds` and `feature_counts` into `preprocessing`.
- **The rank sweep** (`run_rank_sensitivity`) provides `_check_reference` (primary analysis vs export hashes, MOTCO version, seed, permutations, `component_selection = cv`), `_sensitivity_row` (one record → flat row), `_csv_float` (shortest round-trip floats) and `render_rank_sensitivity`. `rank_sensitivity.csv` must stay byte-identical, so `_sensitivity_row`'s columns cannot change.
- **The features at stake**: RNA input 36,601 genes, of which chrX 1,148 (including `XIST`, `ENSG00000229807`), chrY 111, chrM 13; ATAC input 218,882 peaks, of which chrX 5,886, chrY 180, chrM 0 (identical in both cohorts). The primary kept 5,000 per omic out of 20,387 / 128,916 (`cohort_30`) and 20,238 / 124,818 (`cohort_50`) that passed the abundance filter.
- **What keeping chrX changes mechanically.** Step 3's library sizes are the totals after chromosome removal, so with chrX present every feature's CPM shifts slightly and the abundance filter can change at its margin; TMM factors and log2-CPM are recomputed on the new filtered set; chrX features enter the variance ranking and compete for the 5,000 slots. A feature with a constant sex offset (`XIST` in females) shifts the two sexes' centroids but not the within-sex displacement between stages, and MOTCO's PLS-DA is stage-supervised, so X-dosage features enter the latent basis only through their covariance with stage. The expectation is therefore a modest change, but it is unmeasured, which is what the variant is for.
- **Where the data are**: `nixos-home` (where this change is proposed) holds `results/motco_input/` and `results/motco_analysis/` (pulled from the cluster) but no `results/pseudobulk/` and no `data/annotation/`. `scripts/sync_pseudobulk.sh` pulls the pseudobulk outputs (tens of MB without the per-donor cache), and `resolve_gene_annotation` downloads the GTF once (internet is available there). The primary export was made on the laptop (`export_git` commit `ab3423a`, 2026-10-16) and its analysis there too (`c2f25e3`, 2026-10-19); floating point differs between the two machines at the one-ulp level, which the export's `%.10g` output is expected, not guaranteed, to hide.

## Goals / Non-Goals

**Goals:**
- One command that, per variant and cohort, writes the variant export, the variant analysis and the comparison from the pseudobulk outputs and the primary export and analysis, with the same provenance discipline as `export` and `analyze`.
- The variant export and the primary export share one code path, so a variant export is the primary export with one keyword changed and nothing else; `export` output stays byte-identical across the refactor.
- The comparison can only be read as sensitivity, and the layout lets later changes run the rank sweep on a variant without new code.

**Non-Goals:**
- Any other variant (other N, residualized features): the registry is designed to take them, none is added.
- Running the forced-rank sweep on the variant, or rerunning the primary export or analysis.
- A verdict on which preprocessing is better, or a replacement of the primary result.
- A pytest suite; verification stays synthetic checks plus the real run.

## Decisions

**D1. Extract the per-cohort body of `run_export` into `_export_cohort`.**
`_export_cohort(cohort, sub, blocks, covariates, annotation, pb_info, *, out_dir, final_name, excluded_chromosomes, variant=None, debug_dir=None, log_prefix="export")` takes the loaded inputs (`sub` = the cohort's rows of the donor table, `blocks` = the loaded matrices with names, gene ids and chromosomes, `pb_info` = the pseudobulk manifest hash and timestamps), computes `k`, runs `preprocess_block(..., excluded_chromosomes=excluded_chromosomes)` per omic, writes the seven files into `<out_dir>/<final_name>.tmp/`, renames and returns `{"dir", "manifest", "findings", "k", "cells"}`. The manifest's `thresholds.excluded_chromosomes` comes from the parameter; a `variant` block (`name`, `description`, `settings`, `reference_export_dir`) is added only when `variant` is given, so the primary manifest's keys are unchanged. `run_export` becomes the input checks, the loading and a loop over cohorts calling the helper with `EXPORT_EXCLUDED_CHROMOSOMES`.
- *Alternative: a second function copying the body.* Rejected: the manifest and file-writing logic would drift, and the variant's claim is that nothing but one setting differs.
- *Verification of the refactor:* a synthetic pseudobulk directory (`rna_counts.h5ad` with `var["gene_ids"]`, `atac_counts.h5ad` with `chrN:start-end` names, `donor_table.csv`, `manifest.json` with `partial: false` and analysable cohorts, `donor_covariates.csv`, `covariates_manifest.json`) plus a hand-made gzipped GTF placed at `<scratch data root>/annotation/gencode.v32.basic.annotation.gtf.gz` so nothing is downloaded. `run_export` before and after the refactor into two scratch directories: the six CSVs byte-identical, `manifest.json` equal apart from `created_at` and `git`. On `nixos-home`, the refactored `run_export` with defaults into a scratch directory is compared with the kept `results/motco_input/<cohort>/`.

**D2. The variants are a registry constant, `PREPROCESSING_VARIANTS`.**
`{"keep_chrx": {"description": "chrX kept; chrY and chrM removed; every other export setting equal to the primary", "export": {"excluded_chromosomes": ("chrY", "chrM")}}}`. The runner passes each variant's `export` dict as keyword arguments to `_export_cohort`, so a later variant is one more entry (an `other N` variant would carry `top_n`; residualized features would need a new step and are deferred by decision). The analysis has no per-variant settings: it is always the primary's.
- *Alternative: an `--excluded-chromosomes` flag on `export`.* Rejected: scientific settings are constants here, never flags, and a flag invites variants chosen after seeing results.
- *Alternative: append the chrX features to the primary blocks.* Rejected: unequal N across blocks (MOTCO z-scores features without block weights), stale CPM and TMM, and it would not be "the primary pipeline with one setting changed".

**D3. Reference checks run before anything is written.**
Two checks per cohort, both read-only:
- `_check_export_reference(primary_export_dir, pb_dir, annotation, k, cells, n_donors)` reads `results/motco_input/<cohort>/manifest.json` and compares `input.pseudobulk_manifest_sha256` and `input.covariates_manifest_sha256` with the files now in the pseudobulk directory, `annotation.sha256` with the resolved GTF, `thresholds` (`excluded_chromosomes` = `EXPORT_EXCLUDED_CHROMOSOMES`, `min_cpm`, `prior_count`, `N`, `tmm.logratio_trim`, `tmm.sum_trim`, `float_format`) with the constants, and `thresholds.k`, `metadata.cells`, `n_donors` with the values computed now from `donor_table.csv`. Any difference is a `ValueError` naming the file or setting and the `export` command. It returns the primary export manifest and the sha256 of its five analysis-input files.
- `_check_reference(primary_export_dir, primary_analysis_dir, inputs, motco_version)`, reused unchanged from the rank sweep, with `inputs = load_analysis_inputs(primary_export_dir)["inputs"]`.
The variant export's `metadata.csv` and `covariates.csv` are then required to be byte-identical to the primary's (same donors, same covariate rows), a cheap end-to-end check that the pseudobulk inputs are the primary's; a difference is an error, not a finding.
- *Alternative: trust the directories.* Rejected: a pseudobulk or annotation regenerated after the primary export would make the comparison a comparison of two pipelines, not of one setting.

**D4. Output layout mirrors the primary pipeline.**
`results/motco_sensitivity/<variant>/motco_input/<cohort>/`, `.../motco_analysis/<cohort>/`, `.../comparison/<cohort>/`. Each cohort directory is written as `<cohort>.tmp/` and renamed, in the order export → analysis → comparison, so the export is in its final place before `_analyze_cohort` reads it and records its path; a cohort is complete when its comparison directory exists. Any of the three existing is an error without `--force`; with `--force` all three are replaced. The mirrored layout is what lets `rank-sensitivity --input-dir results/motco_sensitivity/keep_chrx/motco_input --analysis-dir results/motco_sensitivity/keep_chrx/motco_analysis --out-dir ...` run on a variant later with no code change, and it keeps `_analyze_cohort` free of path rewriting.
- *Alternative: `<variant>/<cohort>/{export, analysis, sensitivity.*}` under one `.tmp` per cohort.* Rejected: the atomicity gain is small (the comparison directory already marks completion) and the rank sweep would need a flag or symlinks to read it.

**D5. The variant analysis is one `_analyze_cohort` call with the primary's parameters.**
`_analyze_cohort(cohort, variant_export_dir, load_analysis_inputs(variant_export_dir), TrajectoryAnalysisParams(permutations=ANALYSIS_PERMUTATIONS, seed=ANALYSIS_SEED, n_jobs=n_jobs), out_dir=<variant>/motco_analysis, final_name=cohort, n_jobs=n_jobs, findings=[f"preprocessing variant {name}: the primary analysis in {primary_dir} is primary"], log_prefix="preprocessing-sensitivity")`. CV rank selection runs as in `analyze` (MOTCO defaults, `random_state = 1203`). The same seed and permutation count mean RRPP draws the same permutation indices as the primary, so between-variant differences are data differences, not draw differences. The resulting `analysis_manifest.json` copies the variant export's manifest into `preprocessing`, so `excluded_chromosomes = [chrY, chrM]` and the variant's feature counts are visible there, and its `cli_equivalent` reproduces the variant with `motco analyze` on the variant's blocks.

**D6. Comparison table, feature accounting and renderer.**
`_variant_row(record, *, variant, cohort, directory)` wraps `_sensitivity_row` and inserts `variant` as the first column (`primary` / `keep_chrx`); `sensitivity.csv` is the two rows without `runtime_seconds`, written with `_csv_float`. `dir` is the primary analysis directory for the primary row and `motco_analysis/<cohort>` relative to the variant root for the variant row. `_feature_accounting(primary_export_dir, variant_export_dir)` reads both `features_<omic>.csv` files and manifests: per omic, both exports' `feature_counts`, the variant's kept features on chrX (count and names), kept shared / primary-only / variant-only (sets of `kept` names), and a check that no chrX feature of the variant carries `sex_chromosome`. `render_preprocessing_sensitivity(rows, features, *, variant, cohort, seed, permutations, alpha)` writes a header naming the variant, its settings, seed, permutations, α and both ranks; one table per statistic (two rows); a feature table; a run table (rank selection, CV AUROC, runtime, directory). Findings: ranks differ; a statistic's rejection status differs (preprocessing dependence, the primary stays primary); `n_jobs ≠ 1`; the variant export's own findings (fewer than N features, unmapped genes) copied through.

**D7. CLI.**
`sead-sexdiff preprocessing-sensitivity [--variant {keep_chrx,all}] [--cohort {cohort_30,cohort_50,all}] [--pseudobulk-dir results/pseudobulk] [--input-dir results/motco_input] [--analysis-dir results/motco_analysis] [--out-dir results/motco_sensitivity] [--data-root …] [--n-jobs 1] [--force]`, printing `[preprocessing-sensitivity]` progress (export steps per omic, analysis rank and runtime, the comparison rows) and the comparison table at the end. `--n-jobs` carries the same note as `analyze`.

**D8. A separate dated report.**
`reports/motco-astrocyte-chrx-sensitivity-<date>.md`, assembled by a scratch script that pastes each cohort's `sensitivity.md`, with hand-written provenance (MOTCO 0.8.0 commit, this repo's revision, seed, permutations, `n_jobs = 1`, the pseudobulk and annotation hashes, the primary export and analysis hashes), the reading rules the spec binds, the chrX limitations, and a pointer to `reports/motco-astrocyte-2026-10-19.md` for the covariate block. Descriptive checks added if they hold: the status of `XIST` and the count of kept chrX features per omic in the variant export; the sign-aligned Pearson correlation of `pls_0` scores between the primary and the variant analysis, and the stage means along `pls_0` per sex in both; the CV AUROC of both. A check script finds every statistic, p-value, null summary, rank and feature count from the four records and two comparison manifests in the report text.
- *Alternative: append to the primary or rank-sensitivity report.* Rejected: those are checked records at a commit; this run has its own provenance and date.

**D9. The real run happens on `nixos-home` after syncing the pseudobulk outputs.**
`scripts/sync_pseudobulk.sh` (without the per-donor cache) brings `results/pseudobulk/`; the first `preprocessing-sensitivity` or `export` call downloads the GTF into `data/annotation/` (`data/` is gitignored, `SEAD_DATA_ROOT` unset there). Before the variant runs, the refactored `run_export` with defaults is run into a scratch directory and compared with the kept `results/motco_input/<cohort>/`: byte-identical CSVs validate both the refactor and the machine; a last-digit difference is recorded in the task and does not block the run, because the reference checks hash the inputs (pseudobulk manifest, annotation) and the primary pair (export files vs analysis manifest), never the variant against the primary CSVs. Byte-identity checks of the variant itself compare two runs on the same machine.

## Risks / Trade-offs

- [A variant rejection gets read as "the" result, or the variant becomes the new primary] → the registry is a constant, the primary row is first in every table, and the spec fixes the report wording (preprocessing dependence, primary unchanged).
- [X-dosage features enter the blocks and MOTCO's operating characteristics have no such features] → stated as a limitation; the variant carries no Type I or power claim; the feature accounting (kept chrX counts, `XIST` status) is reported beside the results so the reader sees how much entered.
- [A different CV-selected rank in the variant changes what `angle` measures] → reported beside `angle` and as a finding, never as better or worse; the forced-rank sweep on the variant is a later change the layout already allows.
- [Cross-machine floating point between the laptop-made primary and the `nixos-home`-made variant] → the comparison reads statistics and p-values from records and never requires byte-identity between primary and variant; D9 records the outcome of the primary-export reproduction.
- [The pseudobulk outputs or the annotation on disk are not the ones the primary export used] → D3's hash checks stop the run naming the file.
- [The refactor changes `export` output] → D1's byte-identity check on synthetic data before the real run and D9's reproduction on `nixos-home`.
- [Data are not on this machine] → sync and annotation download are the first tasks of the real-run group; everything before it runs anywhere.
